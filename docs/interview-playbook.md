# TraceForge 面试讲述手册

TraceForge 的主线是：**把一次修复变成有来源、需审批、可验证、能恢复的工程过程。** 面试时优先展示证据与失败处理，再讨论模型。当前已有真实模型端到端记录，以及固定十个合成案例上的功能、拒答与安全实测。

本文是讲述材料，最新验收结果以 [acceptance.md](acceptance.md) 为准。测试数量、报告分母和服务可用性会变化，演示前重新核对，不背诵过期数字。

## 两分钟介绍

> 我做了一个本地工程故障调查工作台，叫 TraceForge。它解决的问题是：模型给出的解释和补丁看起来合理，但开发者仍要核对代码出处、判断能不能改，以及确认修改确实解决了问题。
>
> 我的实现把这条链路串了起来。用户注册仓库、提交异常，系统并行收集源码、日志和 Git 证据；一个有步数和时间预算的 Agent 可以继续搜索、读取文件，最后提交带证据引用的结构化诊断。引用要来自实际取证结果，补丁要通过路径和精确替换校验。用户批准绑定 SHA256 摘要的方案后，系统才在独立快照里执行基线测试、应用补丁、再跑回归，原始仓库保持只读。
>
> 我花得最多的精力是防止“看起来成功”。例如，早期只解析控制台里的测试摘要，恶意实现可以打印“测试通过”然后提前退出。我实际复现了这个问题，后来引入仓库外的测试观察器，记录测试身份和结果。退出码变成零，但观察报告缺失、原测试被替换或跳过增加，都不能记作已验证修复。这个机制已在 Windows 上结合 Docker 实际跑通。
>
> 另外，审批和状态迁移都持久化到 SQLite，worker 用租约恢复任务，重复审批或旧 worker 写入会被拒绝。检索使用 BM25、字符 n-gram TF-IDF 和 RRF；并行部分是取证任务，核心是单 Agent。
>
> 效果上我分开报告：离线演示和 Oracle 基准验证机制，真实模型调用单独记录。通过本地网关请求 deepseek-v4.1-flash 的一次十案例实测中，7 个修复案例通过公开与隐藏测试，3 个应当不改代码的案例保持无补丁，2 个带提示注入的安全案例通过契约检查。总计 25 次请求、约 9.1 万 tokens。这是很小的合成样本，不代表生产故障修复率。

正常语速约两分钟。被打断时停在当前证据点，直接展开面试官关心的问题。

## 按追问展开架构取舍

| 追问 | 建议回答 | 可打开的证据 |
| --- | --- | --- |
| 为什么做这个项目？ | 选的是“从建议到可采纳修改”的工程链路。一次修复是否可信，要能回答依据是什么、批准的是哪份内容、测试是否真的执行、失败后如何恢复。 | [README](../README.md)、控制台的证据／补丁／验证／轨迹页 |
| 这是工作流还是 Agent？ | 注册、审批、状态迁移和执行边界是确定性工作流；调查阶段允许模型在 `search`、`read`、`finish` 之间选择。模型没有任意主机 shell。 | [engine.py](../traceforge/engine.py)、[provider.py](../traceforge/provider.py) |
| 你用了多 Agent 吗？ | 当前是单个推理 Agent，源码、日志、Git 等独立取证任务并行。它们不是多个模型角色。增加模型 Agent 要先在固定数据集上证明收益和成本可接受。 | [architecture.md](architecture.md)、`Engine.investigate` |
| 为什么不用向量数据库？ | 当前任务中标识符、报错和路径很重要，所以先建立轻量词法基线：BM25 加字符 n-gram TF-IDF cosine，再用 RRF 融合。TF-IDF 不是预训练 embedding；目前没有证据说明神经向量在这个任务集上更好。 | [retrieval.py](../traceforge/retrieval.py) |
| 如何避免编造引用？ | 证据保存来源、路径、行号、内容摘要与哈希。最终诊断引用的 ID 必须存在于本次真实取证集合。引用存在只能说明材料可追溯，不自动证明因果结论正确。 | [models.py](../traceforge/models.py)、[engine.py](../traceforge/engine.py) |
| 为什么用精确替换？ | `before` 必须唯一匹配，修改路径必须在范围内；这样审批内容与实际变更容易对应。代价是对上下文变化敏感，也不擅长大规模结构重写，遇到不匹配会失败而非猜测应用。 | [runner.py](../traceforge/runner.py) |
| 为什么 SQLite 而非 Redis／消息队列？ | 当前是单机本地工具，SQLite WAL 降低部署成本。事务把审批、状态与审计记录绑定；任务租约允许恢复。处理语义是至少一次，崩溃后可能重复请求或创建新副本，不能称为 exactly-once。 | [store.py](../traceforge/store.py)、[test_process_recovery.py](../tests/test_process_recovery.py) |
| 重复请求和旧 worker 怎么处理？ | 审批校验状态及补丁摘要，重复或过期审批返回冲突。worker 写入受当前租约约束；失去所有权的旧 worker 不能继续修改任务结果。 | [test_store.py](../tests/test_store.py)、[test_api.py](../tests/test_api.py)、[test_engine.py](../tests/test_engine.py) |
| 为什么仍需要人工审批？ | 模型建议与执行权限分开。审批绑定确定的补丁内容，不是笼统授权未来任意修改；源文件版本变化也需要被识别。用户看过的内容必须与验证器将应用的内容一致。 | `patch_digest`、审批接口、源码指纹检查 |
| Docker 是否绝对安全？ | Docker 默认无网络、限制资源、只读根文件系统，仅工作快照等必要位置可写。它提供执行隔离，但项目没有证明能抵御所有容器逃逸。local 只给明确可信仓库；临时目录和 subprocess 不构成安全沙箱。 | `_docker_command`、[Docker 验收摘要](evidence/docker-validation.json) |
| 测试全绿是否足够？ | 还要确认基线实际失败、原测试身份保留、测试数未减少、跳过未增加，并取得完整观察报告。普通仓库执行注册的测试命令，内置 benchmark 额外运行预设隐藏测试检查过拟合。即使这些成立，结论仍只覆盖已执行的测试。 | `assess_regression`、[test_runner.py](../tests/test_runner.py)、[benchmark.md](benchmark.md) |
| 模型接口接通了吗？ | 已使用用户指定网关的 deepseek-v4.1-flash 完成真实工具调用、浏览器审批与 Docker 回归。十案例为每题一次；旧网关 403 等失败仍保留。请求模型名称可以审计，但网关返回不构成底层模型身份认证。 | [真实模型验收](live-validation.md)、[live 报告](evidence/live-run-report.md) |
| 记忆是不是自动学习？ | 只把通过回归验证的结果保存成可审阅的项目经验。目前不自动注入旧记忆进行推理，也没有训练模型。这样避免把过期引用当作新任务证据。 | `save_memory`、控制台“知识记忆” |
| 上线和 CI 到什么程度？ | 已有 Windows 本机、真实 Docker 和浏览器交互验证。GitHub 工作流覆盖 Linux / Windows、两种 Python 版本、前端与独立安装；讲述时打开对应提交的 Actions 结果。仓库托管与 CI 不等于服务已部署或有生产用户。 | [验收记录](acceptance.md)、[GitHub Actions](https://github.com/zhyzx35607/TraceForge/actions) |

## 可以深入讲的真实故障

每个例子按“触发条件 → 错误信任 → 修复 → 剩余边界”讲。未在当前环境重跑时，只说仓库包含回归用例，把运行结果指向验收记录。

**审批过期与并发审批。** 用户审阅的是补丁 A，提交时内容或任务状态已经变化，不能把旧同意用于新内容。系统把审批与补丁摘要绑定，并在事务中检查状态；错误摘要和重复审批返回 409，验证任务只入队一次。对应 `test_approval_digest_gate_via_api` 及 Store 并发审批测试。这解决的是确定补丁的授权一致性，不代表无需审阅补丁质量。

**进程恢复与失效租约。** “任务能重启”还不够：新 worker 接管后，旧 worker 的迟到结果也可能覆盖新状态。实现中保留持久化检查点并校验租约所有权；回归覆盖等待审批时进程重启、租约重新分配、旧 worker 写入和异常回写。恢复语义仍是至少一次，模型服务可能收到重复调用；项目没有自动推送、部署等外部副作用。

**不可信材料与读取边界。** 合成日志中存在伪系统指令，基准将其作为数据处理；安全指标与功能指标分别计算。审查还实际复现并修复了带前缀凭证字段漏脱敏，以及 `.git` 文件、`commondir`、对象 `alternates` 三类指向仓库外的 Git 元数据路径。单靠 `git rev-parse --show-toplevel` 不能证明读取没有越界，现在在执行 Git 前检查元数据布局并拒绝这些外指形式。相关测试位于 [test_retrieval.py](../tests/test_retrieval.py) 和 [test_connectors.py](../tests/test_connectors.py)。Oracle 案例通过只证明执行机制对已知材料的行为，尚不能证明真实模型普遍抵御提示注入。

**伪造测试成功。** 一个候选实现打印 `Ran 100 tests ... OK` 后调用 `os._exit(0)`，退出码和文本摘要都像成功，但真实测试没有完整执行。修复后 stdout 摘要仅作为展示材料；仓库外观察器提供测试身份、逐项结果和完成标记。该复现返回“观察报告缺失或无效”，不记录修复成功；替换掉原测试身份，即使测试总数增加，也被拒绝。外部观察器已与 Docker 实测成功。观察器仍与 Python 测试共享进程语义，反射或 monkey-patching 不是密码学意义的防篡改保证，这个限制写入验证报告。

**引用的版本一致性。** 只比较调查开始和结束时的文件哈希不够：文件可能经历 A → B → A，而工具返回的是 B。系统现在在证据进入模型前绑定调查 manifest，恢复时同时核对证据目录和历史工具消息，空仓库的 `{}` manifest 也视为确定版本。回归测试在一次读取内完成临时修改与恢复，确认模型不会接收到错版本证据。

**测试到底在哪份代码上执行。** 测试命令的绝对路径、pytest 配置和 editable 安装可能把测试导回原仓库；仅设置 cwd 不能证明测试在副本上执行。修复把受支持的参数映射到快照并核对真实模块与测试定义来源。回归复现了“候选补丁无行为变化，外部源文件变好，测试却显示已修复”的误判，随后阻止该误判。

**检索融合的收益与代价。** 原来每案只有 4–6 文件，Top-8 的 10/10 连字母排序都能达到。合并公开语料并移除题面后，RRF 的 Recall@8 高于 BM25，但 MRR 低于 BM25。可以据此说明为什么要做消融、如何定义分母与避免题面泄漏；不能声称 RRF 在所有指标上更好。完整数字与逐案例差异见 [检索消融](retrieval-evaluation.md)。

## 真实效果怎么报

| 结果类型 | 可以说 | 不能换算成 |
| --- | --- | --- |
| `replay` 内置演示 | 固定候选补丁走完真实取证、审批和回归链路 | 模型自主定位并修复 |
| `oracle` 多故障基准 | 已知补丁的验证器正确率；公开与隐藏测试实际执行 | LLM 修复准确率 |
| `retrieval` | 所需路径是否出现在初始检索集合，按报告分母计算 | 已确定根因或模型理解准确率 |
| `live` | 实际请求、工具行为、用量和失败原因 | 未成功运行时的推理能力或可靠性 |
| 测试和浏览器验收 | 此版本在已列环境、命令和样例下的观察结果 | 企业上线收益、用户规模、生产稳定性 |

仓库内结算夹具在一次实际 Docker 验证中，基线执行 8 项、4 项失败；修复后 8 项全部通过，观察来源为 `external_observer`。这是该夹具的可复现观察，不是全项目测试总数或通用修复率。新的数字均从 [acceptance.md](acceptance.md) 和对应原始报告读取。

## 可复制的简历表述

只保留自己能解释并现场复现的条目。使用 AI 辅助开发时，不声称全部代码由个人手写；可以说明自己负责问题定义、架构选择、验证与迭代，并明确工具参与范围。

**项目描述：**

> TraceForge｜本地工程故障调查与补丁验证工作台，采用 Python/FastAPI、SQLite、React/TypeScript；串联代码取证、结构化诊断、内容绑定审批、独立快照回归验证与审计记录。

**技术贡献候选：**

- 实现 BM25、字符 n-gram TF-IDF cosine 与 RRF 词法混合检索，保留文件行号和内容哈希；统一敏感路径过滤、边界校验和证据脱敏。
- 设计有界 `search/read/finish` 工具循环与结构化输出校验，将模型探索与确定性审批、执行策略分开；持久化实际调用用量与失败状态。
- 用 SQLite 事务、补丁 SHA256 和 worker 租约实现审批一致性、可恢复任务及失效 worker 写入约束，明确采用至少一次处理语义。
- 构建 Docker 快照验证和仓库外测试观察器，核验基线失败、测试身份保留与修复后结果；增加伪造 stdout、提前退出、测试替换等回归用例。
- 构建区分 Oracle、纯检索与真实模型的多故障评测报告，分别展示功能、拒答、安全和检索指标，并为不适用指标保留零分母“未测”。

不要添加“降低故障处理时间 X%”“服务 N 家企业”“百万级代码库”“多 Agent 准确率 100%”等没有实验或业务记录支撑的指标。当前最有力的讲述是一次可复现失败如何推动了边界和验证设计的改变。

## 面试前最后核对

- 能从 UI 的一条证据定位到源文件，并解释引用存在与根因成立之间的区别。
- 能说清自己选用的状态迁移、审批摘要和租约检查分别解决哪种竞争问题。
- 能现场解释一次 stdout 伪造为什么退出码为零仍不算成功。
- 能区分当前已实测结果、只写了配置的能力，以及真实服务仍阻塞的部分。
- 现场演示按 [demo-script.md](demo-script.md) 执行；优先把时间花在可观察结果，而不是念技术栈。
